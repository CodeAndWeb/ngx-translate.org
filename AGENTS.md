# Agent instructions for ngx-translate.org

This repository builds the ngx-translate documentation website with Astro and
Starlight. Library implementation and behavioral tests live in `ngx-translate/core`.

## Repository map

| Location                              | Purpose                                                             |
| ------------------------------------- | ------------------------------------------------------------------- |
| `src/content/docs/`                   | Current documentation in Markdown and MDX                           |
| `src/content/docs/v*/`                | Archived documentation for earlier library versions                 |
| `src/content/versions/`               | Archived version navigation snapshots                               |
| `astro.config.mjs`                    | Current navigation, versions, integrations, and component overrides |
| `src/components/`, `src/styles/`      | Shared site components and styling                                  |
| `src/pages/`                          | Routes outside the documentation collection                         |
| `public/`, `src/assets/`              | Static files and imported assets                                    |
| `recipe-verify/src/app/recipes/`      | Angular compilation checks for documentation examples               |
| `.agents/skills/`, `skills-lock.json` | Project writing skills managed by the Skills CLI                    |

## Setup and validation

Use pnpm and a Node.js version supported by the installed Astro and Angular
toolchains. The site and `recipe-verify/` have separate dependencies and lockfiles;
install each where needed and preserve both `pnpm-lock.yaml` files.

Run these commands from the repository root:

| Task                        | Command                                              |
| --------------------------- | ---------------------------------------------------- |
| Install site dependencies   | `pnpm install --frozen-lockfile`                     |
| Serve the site              | `pnpm dev`                                           |
| Check and build the site    | `pnpm build`                                         |
| Preview the built site      | `pnpm preview`                                       |
| Install recipe dependencies | `pnpm --dir recipe-verify install --frozen-lockfile` |
| Compile recipe examples     | `pnpm run verify-recipes`                            |

- Run `pnpm build` for documentation, site code, or configuration changes. It runs
  Astro checking and the production build, including the configured link validator.
  Fix failures introduced by the change and report any pre-existing blockers.
- For changed Angular examples, update the corresponding verification files and
  run `pnpm run verify-recipes`. Follow the minimal stubs in
  `recipe-verify/src/app/recipes/_template.ts` and add new files to `recipes/index.ts`.
  This checks compilation against the packages installed in `recipe-verify/`;
  it does not establish runtime behavior or validate an unbuilt core branch.
- For layout or component changes, inspect affected pages in the browser at desktop
  and mobile widths, including keyboard navigation.
- For instruction-only changes, check formatting, referenced paths, and
  `git diff --check`; a site build is unnecessary. Format only touched files using
  their local conventions. `dist/` and `.astro/` are generated output.

## Documentation conventions

- Check `astro.config.mjs` for the current version. Make current-version changes
  in the unversioned documentation tree. Change archived pages only when the task
  applies to those versions; preserve their APIs and version-prefixed links.
- Preserve frontmatter such as `title`, `description`, and `slug`. Public URLs use
  the slug, not the numbered source filename. Keep existing URLs and anchors stable,
  and update affected links when a route or heading changes.
- Read neighboring pages before adding content. Use MDX when a page needs imported
  components, and reuse existing Starlight or project components. Keep code fences
  labeled with their language and include imports needed to understand examples.
- Current getting-started and reference navigation is explicit in
  `astro.config.mjs`; recipes and resources use autogenerated navigation. Update
  the relevant navigation when adding a page. Archived navigation is stored in
  `src/content/versions/`.
- Verify API names, defaults, error behavior, and compatibility against the target
  library version's source and tests. Keep unreleased behavior identified as such;
  do not infer supported Angular versions from the recipe workspace's toolchain.

## Writing skills

When writing or revising documentation prose, read and apply both project skills:

1. [i-have-adhd](.agents/skills/i-have-adhd/SKILL.md) for clear first actions,
   short sections, and numbered procedures. Preserve all necessary prerequisites,
   API details, and failure behavior.
2. [humanizer](.agents/skills/humanizer/SKILL.md) for the final prose pass. Use file
   mode for documentation and embedded mode for PR text. Preserve technical claims,
   code, commands, paths, link targets, and frontmatter during this pass.

Published pages must stand alone. Keep chat progress reports and prompts out of
the documentation, and retain the neutral voice appropriate to technical reference.

Manage the installed skills with the Skills CLI so their sources and hashes remain
recorded in `skills-lock.json`. Restore them with `npx skills experimental_install`;
run `npx skills update --project` when an update is requested. Commit changed skill
files and their lockfile entries together. Put project-specific guidance here
instead of editing the installed upstream skills.

## Coordinating with core

- Use the sibling `../core` checkout when available and read its agent instructions
  before working there. Confirm its branch and the comparison base when documenting
  a change; distinguish committed behavior from local modifications.
- The core project's `sync-doc` skill describes the branch-to-documentation PR
  workflow. Use it when asked to sync a core branch, rather than running a sync for
  every documentation edit.
- Documentation PRs belong in `CodeAndWeb/ngx-translate.org`; library changes belong
  in `ngx-translate/core`. Keep them in separate PRs and cross-link related work.
  Describe the behavior documented and the validation performed.
- Cloudflare Workers Builds deploys pushes to `main` as documented in `README.md`.
  Prepare changes on a topic branch and use a PR for review.
